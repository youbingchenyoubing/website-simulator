## 2. 核心难点：如何"拦截官方地址"

用户初步设想是"自定义浏览器，拦截官方地址"。有 3 条可行路线：

### 方案 A：Electron + Session 拦截（⭐推荐）
自研一个 Electron 壳浏览器：
- `ses.webRequest.onBeforeRequest` / `protocol.handle` 拦截命中映射表的域名，将请求重写到本地 mock server（如 `http://127.0.0.1:8080/amazon/...`）；
- 地址栏是自己渲染的 UI，天然显示用户输入的官方域名；
- 未命中域名默认阻断（弹"模拟环境不可访问外网"页）。

**优点**：全链路可控、跨平台、团队 JS 技术栈即可。
**缺点**：安装包 ~150MB；HTTPS 域名只是"显示"，真实证书无需处理（因为请求根本没出本机）。

### 方案 B：系统代理 / 本地 DNS + 反向代理
不改浏览器，用真实 Chrome：
- 本地起 DNS（如 `dnsmasq`）或改 hosts，把目标域名指到 127.0.0.1；
- 本地 Nginx/Caddy 用自签 CA 签发域名的 TLS 证书，反代到 mock server。

**优点**：用真实浏览器，体验最真。
**缺点**：要安装自签根证书、改系统配置，环境准备复杂；**与钓鱼技术完全同源，合规风险最大**，不推荐。

### 方案 C：纯 Web"画中画"
普通网页里嵌一个假的"浏览器 chrome"（网址栏是 UI 装饰）。

**优点**：零安装，打开即用。
**缺点**：地址栏一眼假，不适合"打开的是官方网址"的诉求；只适合对仿真度要求低的场景。

**结论：采用方案 A（Electron），方案 C 作为低配 fallback。**

## 3. 技术选型

| 模块 | 选型 | 理由 |
|------|------|------|
| 客户端壳 | Electron 28+ | 见方案 A |
| 模拟站点前端 | React 18 + Vite + Tailwind / Ant Design | 快速重绘卖家中心类后台 UI |
| 服务端 | Node.js (NestJS 或 Express) | 与前端同栈，单人可维护 |
| 数据库 | SQLite（Prisma ORM） | 单机零依赖；ORM 便于未来换 PG |
| 后台管理 | 与服务端同工程，独立路由 `/admin`，React Admin 或 Ant Design Pro 简化版 | 降低工程量 |
| 部署 | docker-compose（server + admin），客户端 Electron 打包分发 | 一键演示 |

## 4. 关键设计

### 4.1 拦截规则表
```json
[
  { "host": "sellercentral.amazon.com", "site": "amazon",  "enabled": true },
  { "host": "sso.geiwohuo.com",          "site": "shein",   "enabled": true }
]
```
客户端启动时从 server 拉取（本地缓存兜底）。`site` 决定渲染哪套平台模板。

### 4.2 模拟登录
- 登录页提交到 mock server `/api/auth/login`；
- 命中后台"可用账号表"则按角色返回对应场景数据；未命中可配置为"一律成功（演示模式）"或"失败提示";
- 发 HttpOnly cookie，会话内存存储，重启即清空。

### 4.3 数据模型（核心表）
```
Scenario(id, name, site, status, ...)        -- 场景
Shop(id, scenarioId, name, metrics JSON)     -- 店铺与指标
Product(id, scenarioId, title, price, stock, sales, image, ...)
Order(id, scenarioId, productId, amount, status, createdAt)
MockAccount(id, username, password, scenarioId)
```
所有业务接口强制携带 `scenarioId`，实现"数据可定制、可切换"。

### 4.4 页面数据解耦
页面组件只读 `/api/pages/<pageKey>?scenarioId=x` 返回的 JSON Schema 数据；模板中**禁止硬编码业务数值**（对应 F-206）。

### 4.5 合规技术兜底（对应需求文档 §2）
1. 服务端默认绑定 `127.0.0.1`，配置项放开需显式确认；
2. 全局悬浮水印组件（页面右下角"模拟环境"+ 顶部细条），由模板基座强制注入，业务页无法移除；
3. 登录接口不落盘记录用户输入的密码字段。

## 5. 项目结构（建议 monorepo）
```
website-simulator/
├── apps/
│   ├── client/      # Electron 壳浏览器
│   ├── site/        # 模拟站点前端 (React)
│   └── admin/       # 管理后台前端

│   └── prisma/

```

## 7. 风险与对策
| 风险 | 等级 | 对策 |
|------|------|------|
| 合规/法务风险（技术形似钓鱼） | 🔴 高 | 严格执行需求文档 §2 全部约束；上线前法务评审 |
| 官方页面改版导致模板过时 | 🟡 中 | 模板按"布局神似"而非像素级拷贝，降低维护成本 |
| Electron 体积大、分发重 | 🟢 低 | 提供方案 C 纯 Web 低配版作为备选 |
| 数据配置繁琐 | 🟡 中 | 后台提供"场景模板 + 订单批量生成"降低配置成本 |
